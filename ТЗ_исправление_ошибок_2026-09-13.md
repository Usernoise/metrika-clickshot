# ТЗ на исправление ошибок ClickShot Metrika

Дата: 13.09.2026. Объект: локальная версия проекта metrika-clickshot.

> Обновление после реализации: исходные наблюдения ниже описывают версию до исправлений.
> Подтверждённые дефекты исправлены в рабочем дереве; актуальная команда проверки —
> `bash tests/check.sh`. Сохранён контракт: ClickShot и цели баннера работают до согласия,
> разрешение Яндекс.Метрики проверяется отдельно. Добавлены CLI-миграция, резервная копия,
> лимиты без IP/идентификаторов и CI. Рабочая/production-база не изменялась.
> Очистка старой истории, исправление уже существующих некорректных ID, расписание бэкапов,
> подбор лимитов под production и юридическая оценка остаются отдельными работами.
> Произвольные сторонние загрузчики/статические теги Метрики не стали поддерживаться:
> ограничение явно описано, проверка установки предупреждает о распознаваемых случаях.

## 1. Результат и границы аудита

Изучены PHP-библиотека, все HTTP-обработчики, счётчик, Slide Cookie, JavaScript дашборда, схема SQLite, штатные тесты, README, пример Caddy и исходное функциональное ТЗ. Приложение — PHP + SQLite + обычный JavaScript; название родительского каталога Python не отражает стек.

Воспроизведены 11 нарушений контрактов на изолированной SQLite-базе и в JavaScript VM. Дополнительно выявлены проблемы по исходникам и эксплуатационные риски, для которых ниже указан отдельный уровень доказанности. Подтверждённых P0 — удалённого выполнения кода, обхода авторизации администратора, массовой потери рабочей базы — не найдено. Есть P1: искажение аналитики, неполное удаление данных, пропуск чувствительных значений и неработоспособные счётчики.

Это аудит локального кода, а не заключение о состоянии production. Сервер, реальные сайты клиентов, рабочая база, внешние резервные копии и настройки PHP-FPM/CDN не проверялись. Браузерные сетевые сценарии Slide Cookie и производственная нагрузка не воспроизводились. Исчерпывающую гарантию отсутствия других ошибок аудит не даёт.

Приоритеты: P1 — исправить до ближайшего выпуска; P2 — следующий обязательный этап; P3 — улучшение сопровождаемости. «Воспроизведено» означает запуск реального HTTP-кода либо реального JavaScript с контролируемым окружением. «По коду» — установлен конкретный дефект реализации, но соответствующее окружение не запускалось. «Риск» — не утверждение о состоявшемся инциденте.

## 2. Проверки и воспроизведение

Окружение: PHP CLI 8.4.6, Node.js 22.22.3; SQLite, mbstring и curl локально доступны. Production-цель по документации — PHP 8.3, её необходимо включить в итоговую приёмку.

Команды из корня проекта:

```sh
php tests/dashboard_tabs_test.php
php tests/source_filter_contract_test.php
node tests/audit_repro.mjs
```

Оба штатных теста прошли. Синтаксис всех PHP-файлов, обоих внешних JS-файлов и встроенного JS дашборда корректен. Штатные тесты ищут строки в исходниках и не проверяют расчёты, HTTP-валидацию или поведение интерфейса.

Диагностический сценарий `tests/audit_repro.mjs` создаёт свою базу в системном временном каталоге, запускает PHP только на localhost со случайным портом, останавливает процесс в `finally`. Не использует базу `storage/metrika.sqlite`. Требует PHP с PDO SQLite и mbstring, а также Node 22. Временную базу оставляет для исследования; путь выводит в конце. Код завершения 1 сейчас ожидаем: обнаружены ошибки.

Фактический результат последнего запуска:

## 3. Задачи P1

### CS-01. Исправить проверку домена отправителя

Доказанность: воспроизведено. Места: `public/api/hit.php:35`, аналогичный условный блок `public/api/config.php:19`.

Проверка включается только при непустом распознанном Origin. Без него запрос принимается даже с чужим Referer. Публичный ID сайта достаточен для записи произвольных событий без каких-либо заголовков происхождения. Это нарушает исходное ТЗ. Дополнительно чужой Origin разрешается при допустимом Referer.

Требования:

- Вынести единую политику: если Origin присутствует, проверить его корректность и точное совпадение нормализованного hostname; при чужом или некорректном Origin отказать. Referer использовать только при отсутствии Origin.
- При отсутствии обоих допустимых признаков происхождения отклонять событие. Явно обработать `Origin: null`, испорченные URL и порты.
- Возвращать 403 и не изменять агрегаты. Выдавать CORS-заголовки для разрешённых источников, убрать ненужный credentialed CORS, если выбран транспорт без credentials.
- Для публичной конфигурации отдельно зафиксировать, требуется ли ограничение чтения; конфигурация всё равно доступна через loader, поэтому не считать её секретом.

Приёмка: матрица допустимого/чужого/отсутствующего/некорректного Origin и Referer; база не меняется при отказе. Origin и Referer подделываются небраузерными клиентами: эта проверка не заменяет защиту от накрутки и нагрузки, см. CS-16.

### CS-02. Отделить цели от просмотров и визитов страниц

Доказанность: воспроизведено. Место: `public/api/hit.php:68` и независимые блоки на строках 106, 125, 135.

После записи цели обработчик продолжает увеличивать просмотры страниц, источников и технических категорий. Общие daily/hourly при этом не растут. У обычной клиентской цели нет path/referrer, поэтому появляются фиктивные просмотры `/` и прямые заходы. Баннер автоматически отправляет `cookie_consent_shown`, поэтому дефект возникает без ручной интеграции целей. Фильтр источника использует referrer_daily_stats и может показывать другие итоги, чем отчёт без фильтра.

Требования: отдельные ветки обработки pageview и goal. Цель меняет только event_daily_stats и source_event_daily_stats; не увеличивает просмотры/визиты ни в одном разрезе страниц. Зафиксировать отдельную семантику «визитов с целью» и не смешивать её с новыми визитами страницы.

Приёмка: один просмотр + три разных цели = один просмотр во всех включённых разрезах, три события. Повтор одной цели увеличивает events, но не число визитов с этой целью в той же вкладке. Сумма по всем источникам совпадает с общим итогом за период с одинаково включённым сбором. Проверить tech on/off и все комбинации collection.

### CS-03. Передавать источник цели

Доказанность: воспроизведено. Места: `public/counter.js:29`, `public/api/hit.php:45`, отчёт событий в `public/api/stats.php`.

goal отправляет только site/event/newVisit. Любая цель попадает в прямой источник, поэтому цели и конверсия внешнего трафика в фильтре источника пропадают.

Требования: строить контекст pageview и goal общей функцией с учётом collection. При включённых источниках передавать источник; при выключенных — не передавать. Для текущей модели использовать document.referrer, как у pageview. Если нужна атрибуция по первому источнику всей вкладки, оформить её отдельным изменением контракта хранения: сейчас такой модели нет. Path цели передавать только при определённой потребности и включённой категории, не создавать из него просмотр.

Приёмка: вход с `https://search.example/query`, затем goal — цель доступна под `search.example`, не под прямым заходом; полный URL не сохраняется. Внутренний переход обрабатывается согласно выбранной модели. Выключенные категории отсутствуют в payload и новых агрегатах.

### CS-04. Удалять всю статистику сайта

Доказанность: воспроизведено. Место: `public/api/sites.php:183`; схема в `lib.php`.

DELETE пропускает source_page_daily_stats, source_browser_daily_stats, source_os_daily_stats, source_device_daily_stats и source_event_daily_stats. Обещание интерфейса удалить всю статистику не выполняется. Повторное создание того же ID может подмешать старые данные в отчёты по источникам.

Требования: включить все зависимые таблицы в атомарное удаление. Предпочтительно ввести проверенные внешние ключи с каскадом и включить foreign_keys на каждом соединении либо централизовать список зависимостей. Подготовить отдельную миграцию очистки уже существующих сирот с предварительным отчётом и резервной копией. Учесть одновременный hit и DELETE: не разрешать восстановление дочерних записей после удаления.

Приёмка: после удаления ни в одной таблице нет site_id; повторное создание ID даёт нулевую статистику. Сбой в середине удаления откатывает всю транзакцию. Параллельные запросы не создают сирот.

### CS-05. Усилить очистку чувствительных сегментов пути

Доказанность: воспроизведено. Место: `lib.php:307`, функция clean_path.

Примеры, которые функция сохраняет как есть:

```text
/user/%31%32%33%34%35/
/token/ABCDEFGHIJKLMNOPQRSTUVWXYZabcdef/
/phone/+79991234567/
```

URL-декодирование применяется только к проверке email. Числовые ID обходят маску через percent-encoding; длинные токены только из букв и телефон с плюсом не распознаются. Это дефект относительно требований проекта к данным, а не юридическое заключение.

Требования: нормализовать кодирование перед классификацией сегментов с ограниченной глубиной декодирования и обработкой ошибочного UTF-8. Добавить правила чувствительных маршрутов и телефонных сегментов. Для непрозрачных токенов применять консервативное маскирование с возможностью явных шаблонов публичных маршрутов; не обещать распознавание любых персональных данных одной регуляркой. Безопасные SEO-slug сохранить. Провести отдельную оценку ранее записанных путей и подготовить их очистку с пересборкой ключей агрегатов, не теряя суммы.

Приёмка: контрольные пути превращаются в шаблоны с `:id`; тесты также покрывают email, UUID, числовые ID, двойное кодирование, Unicode, query и нормальные SEO-slug. В page_daily_stats и source_page_daily_stats нет исходных чувствительных значений.

### CS-06. Не создавать неработоспособные ID

Доказанность: воспроизведено. Места: `public/api/sites.php:53`, `lib.php:299`.

Автоматический ID не ограничен длиной, тогда как чтение/обновление/удаление разрешает максимум 64 символа. Валидный домен с меткой из 60 букв и суффиксом `.example.com` создаёт ID из 79 символов. Создание успешно, последующие API не находят сайт.

Требования: ограничивать slug с учётом суффикса, валидировать итоговый ID до INSERT, обрабатывать коллизии. Явно переданный неверный ID отклонять, а не молча заменять случайным. Подготовить способ исправления существующих невалидных ID со всеми зависимыми таблицами и заменой сниппета.

Приёмка: длинный корректный домен создаётся, ID ≤64, loader/stats/PUT/DELETE работают; пограничные длины и коллизии покрыты тестами.

### CS-07. Уточнить и обеспечить блокировку Метрики

Доказанность: по коду; сетевой браузерный тест обязателен. Места: `public/slide-cookie.js:180`, `installMetrikaBlock`, `isMetrikaSrc`, `checkActivation`; README и подсказка Slide Cookie.

Перехватывается только присваивание `.src` скрипту, созданному через заменённый document.createElement. Статический script, setAttribute и альтернативные способы создания обходят механизм, даже если ClickShot стоит выше. Ограничение частично описано в комментариях к коду, но пользовательская инструкция обещает блокировку по одному расположению сниппета. При несовпадении UTM-условия блокировка также не ставится, несмотря на включённую настройку «до подтверждения согласия».

Требования: сделать согласие явным условием запуска поддерживаемой интеграции Метрики; определить, какие загрузчики поддерживаются. Предпочтительно управлять загрузкой через один согласованный интеграционный слой. Не полагаться на MutationObserver как гарантию предотвращения уже начатой загрузки. Разделить условие показа баннера и разрешение аналитики либо явно задокументировать их связь. Проверять URL по hostname/path, а не по вхождению подстроки. Диагностика установки должна сообщать неподдерживаемый способ подключения.

Приёмка в настоящем браузере: до согласия нет сетевых запросов Метрики для каждого заявленного поддерживаемого способа подключения; после согласия счётчик запускается один раз. Отдельно проверить отказ, сохранённое согласие, reset_consent, недоступный localStorage, UTM match/mismatch и сбой загрузки ClickShot. Несовместимые интеграции явно обнаруживаются и не объявляются защищёнными.

### CS-08. Исправить зависимости установки

Доказанность: по коду и README; чистая Ubuntu не разворачивалась. Места: `README.md:40`, `lib.php` (mb_substr/mb_strlen), `public/api/check-install.php` (curl_init), `public/health.php`.

Инструкция устанавливает PHP-FPM и SQLite, но не mbstring и curl. Без mbstring обработка хитов и настройки могут завершаться ошибками; без curl не работает проверка установки. Health эти зависимости не проверяет.

Требования: добавить php8.3-mbstring и php8.3-curl в установку, описать минимальную версию PHP и проверить расширения именно в FPM. Health должен проверять все обязательные возможности, возвращать структурированный результат и HTTP 503 при отказе обязательной зависимости/БД, без публичного раскрытия внутренних путей.

Приёмка: установка по README на чистой целевой ОС обеспечивает создание сайта, hit 204, статистику и check-install. Отключение обязательного расширения даёт понятную диагностику, а не необработанный fatal error.

## 4. Задачи P2

### CS-09. Убрать автоматическое восстановление тестового сайта

Доказанность: воспроизведено. Место: `lib.php:230`.

migrate при каждом пустом списке вставляет neural_courses. После удаления последнего сайта следующий запрос восстанавливает демонстрационный проект.

Требования: вынести демоданные в отдельную явную команду/режим установки; пустая база сайтов — штатное состояние. Приёмка: удаление последнего сайта, GET, перезапуск процесса и GET оставляют список пустым. Не удалять существующий пользовательский neural_courses автоматически.

### CS-10. Обработать отказ транспорта

Доказанность: воспроизведено с контролируемым sendBeacon. Место: `public/counter.js:17`.

Если sendBeacon существует, но возвращает false, fetch не вызывается. Маркер визита уже записан, поэтому теряется и событие, и шанс учесть первый визит следующим запросом. Внешний catch скрывает исключения.

Требования: запускать fetch при false/исключении sendBeacon, обрабатывать отказ fetch; возвращать из транспортного слоя результат постановки в очередь и не отмечать заведомо неотправленное событие доставленным. Не считать true у sendBeacon подтверждением записи сервером. Не вводить бесконтрольные повторы после неопределённого результата: без идентификаторов они создают дубли.

Приёмка: true/false/throw/отсутствие sendBeacon, успешный и неуспешный fetch, pagehide и закрытие страницы. При известном отказе обоих способов новый визит не должен навсегда считаться отправленным.

### CS-11. Соблюдать выключение визитов в goal

Доказанность: воспроизведено. Место: `public/counter.js:29`.

goal пишет sessionStorage независимо от collection.visits и доступности конфигурации. Сервер обнуляет visits, но клиент продолжает ненужное хранение. Функция goal становится доступна до завершения загрузки конфигурации.

Требования: общая политика collection для pageview/goal; до получения конфигурации — ограниченная очередь, после ошибки загрузки — предсказуемое поведение без записи отключённых категорий. При выключенных visits не читать/не писать visit-маркеры. Сбор событий при полном выключении остальных категорий описать отдельно: сейчас самостоятельного переключателя событий нет.

Приёмка: goal с visits=false не обращается к sessionStorage; проверены bootstrap, async config, ранняя очередь Slide Cookie и ошибка config.

### CS-12. Валидировать данные после нормализации

Доказанность: пустые домены воспроизведены; остальные границы — по коду. Места: `public/api/sites.php:34`, `lib.php:273`, обработчики API.

domains=[' '] проходит предварительную проверку, затем превращается в [], но сайт всё равно создаётся. Регулярка домена не ограничивает длины меток и допускает некоторые некорректные формы. Нескалярные значения приводятся к строкам или вызывают ошибки вместо контролируемого ответа; например from[]=x в stats несовместим с типом аргумента parseDate.

Требования: типизированная проверка JSON/query до приведений, повторная проверка непустого списка после нормализации, ограничения длины имени, домена, количества доменов и policy_url. Определить поддержку IDN через punycode. Лимит тела проверять до полного чтения в память; валидировать Content-Type для изменяющих запросов. Сохранить серверную проверку независимо от UI.

Приёмка: пустые/пробельные/нескалярные поля, некорректные домены, граничные длины и слишком большой запрос дают 4xx без предупреждений PHP и без изменений БД. Явно протестировать text/plain POST из чужого origin к административному API с автоматически передаваемыми браузером Basic-credentials; добавить проверку происхождения/CSRF-защиту для административных изменений. Эксплуатация CSRF в этом аудите не проверялась.

### CS-13. Предотвратить устаревшие ответы в дашборде

Доказанность: воспроизведено реальной функцией loadStats с отложенными ответами. Место: `public/index.php:364`.

При быстром выборе A → B ответ A может прийти последним и заменить отчёт, пока селектор показывает B. Та же проблема касается периода и фильтров.

Требования: отмена предыдущего запроса и/или монотонный номер запроса; применять ответ только к соответствующей текущей выборке. При ошибке показывать, что данные устарели; очищать все панели при отсутствии сайта. Защитить также асинхронные статусы сохранения настроек и check-install при смене сайта.

Приёмка: ответы B → A оставляют на экране B; аналогично для периода/источников. Старое сообщение об ошибке не заменяет успешный актуальный ответ.

### CS-14. Обновлять формы после создания и выбора сайта

Доказанность: по коду. Место: `public/index.php:658`.

После создания loadSites сохраняет прежний выбранный сайт и заполняет его формы. Затем обработчик меняет select.value на новый ID, но обновляет только snippet и статистику. Формы collection/Slide Cookie остаются от прежнего сайта; последующее сохранение может перенести чужие настройки в новый проект.

Требования: единая функция выбора сайта, которая обновляет все формы, сниппет, фильтры и статусы; использовать её и при change, и после создания/удаления. Приёмка: создать B при выбранном A с нестандартными настройками; все формы и snippet сразу показывают сохранённые настройки B. Сохранение без правок не переносит конфигурацию A.

### CS-15. Сделать проверку установки достоверной и ограниченной

Доказанность: по коду. Место: `public/api/check-install.php`.

Редиректы не отслеживаются, но 3xx считается допустимым ответом и его тело проверяется на сниппет: типичный переход на www даст «код не найден». Поиск двух подстрок во всём HTML допускает совпадения в комментариях и разных скриптах. Граница `\b` после ID может принять id=abc-other за abc. Ответ целиком загружается в память, домены проверяются последовательно по 10 секунд каждый.

Требования: ограниченный обход редиректов с проверкой каждого нового адреса и закреплением публичного IP; сохранить защиту от SSRF. Ограничить общий срок, число доменов и размер тела. Анализировать конкретные script-элементы и точное значение query id, учитывать async/defer и порядок для Slide Cookie. Отделить «код найден в HTML» от «событие действительно принято».

Приёмка: редирект на допустимый публичный адрес, редирект в private network, большой ответ, комментарий со сниппетом, похожие ID и динамическая установка. Последняя должна давать «статически не подтверждено», а не безусловный вывод об отсутствии счётчика.

## 5. Эксплуатационные работы и уточнения контрактов

### CS-16. Ограничить ресурсы публичного приёмника — P1 как защита доступности

Доказанность: риск по коду, нагрузочная атака не выполнялась. В приложении и Caddyfile.example нет ограничения частоты запросов. Для каждого запроса можно менять path/referrer/event и создавать новые строки в SQLite. Размер JSON проверяется после полного чтения; это не ограничивает пиковое потребление памяти на чтении. Реальные внешние ограничения неизвестны.

Требования: ограничить размер запроса на входе, частоту и параллелизм; ввести бюджет новых значений/строк на сайт и период, лимит имён событий или allowlist, наблюдение за свободным диском. Согласовать срок хранения агрегатов. Не вводить постоянные IP-логи и пользовательские идентификаторы в нарушение модели проекта. Перегрузка должна давать контролируемый 429/503. Origin не считать доказательством подлинности отправителя.

Приёмка: согласованный профиль нормальной и повышенной нагрузки, ограниченный рост БД, доступный дашборд во время потока событий. Численные лимиты и целевой RPS выбрать по реальному серверу, не копировать произвольные значения из аудита.

### CS-17. Вынести миграции из запросов и нормализовать ошибки — P2

Доказанность: по коду; конкурентный сбой не воспроизводился. `db()` всегда запускает migrate: DDL, проверку колонок и INSERT OR IGNORE для всех сайтов. Даже чтение статистики пытается писать. Параллельная миграция проверяет колонку отдельно от ALTER, что создаёт окно гонки. В hit исключения БД возвращаются как HTTP 400 с исходным текстом исключения; остальные endpoints местами не ловят сбои БД.

Требования: версионированная миграция с блокировкой и транзакционностью, выполняемая при развёртывании; запросы не изменяют схему и не восстанавливают настройки всех сайтов. Разделить 4xx валидации и 5xx инфраструктуры. Клиенту — безопасный код ошибки, в техническую диагностику — причина без payload, секретов, IP и чувствительных путей.

Приёмка: параллельный запуск миграции на старой копии БД, повторный запуск, откат при сбое. Отдельно проверить занятость SQLite, read-only storage и заполнение диска на изолированном окружении. Чтение статистики не требует права на изменение схемы.

### CS-18. Подтвердить восстановление и расширить автоматические проверки — P1 для процедуры выпуска

Доказанность: в репозитории нет процедуры восстановления/проверки резервных копий и поведенческого CI; наличие внешних бэкапов не установлено.

Требования: перед исправлением исторических данных и схемы делать согласованную резервную копию SQLite с учётом WAL; проверить восстановление отдельной копии и контрольные суммы агрегатов. Определить допустимую потерю данных и время восстановления. Добавить CI на целевой PHP 8.3 с обязательными расширениями, HTTP-тестами и браузерными сценариями. Не ограничиваться поиском строк в исходниках.

Приёмка: восстановление на чистом экземпляре, доступность сайтов/настроек/агрегатов, проверка целостности SQLite. Все CS-01…CS-15 имеют регрессионные тесты соответствующего уровня; сценарии ресурсов проверяются отдельно. Тесты не обращаются к production и не используют его пароль.

### Уточнения, которые не следует выдавать за доказанные критические ошибки

- `collect_pageviews` сейчас отключает общий daily/hourly счётчик, но независимые категории продолжают считать просмотры. UI прямо называет его «Общий дневной и почасовой счётчик», поэтому это неоднозначный контракт, а не однозначно подтверждённый дефект. Зафиксировать семантику: глобальный запрет либо независимые агрегаты. Во втором случае фильтр источника не должен неожиданно менять смысл отключённой метрики; график визитов должен оставаться доступным, если visits=true.
- Визит по вкладке не имеет 30-минутного таймаута, а повторный визит на следующий день в открытой вкладке не засчитывается. Это соответствует исходному приближению; документировать ограничение, не менять модель без отдельного решения.
- Slide Cookie блокирует фон и даёт только принятие; отказа/отзыва согласия в интерфейсе нет, хотя комментарии упоминают отказ. Определить продуктовый сценарий «продолжить без необязательной аналитики» и добавить его, если баннер предназначен для выбора. Это не юридическая оценка достаточности согласия.
- Публичный loader синхронно загружается с сервера ClickShot при включённом баннере. Его задержка влияет на разбор страницы клиента; измерить и согласовать допустимый бюджет, особенно потому, что loader тоже обращается к SQLite.
- Дашборд обращается к Google Fonts; это внешний сетевой запрос администратора. Не путать его со сбором данных счётчиком на сайтах клиентов.
- Существующие старые агрегаты до появления source_* нельзя достоверно восстановить в разрезе источника без исходных событий. В интерфейсе нужна граница доступности соответствующего разреза, а не выдуманное заполнение истории.

## 6. Порядок реализации и финальная приёмка

1. Сохранить и проверить резервную копию; закрепить контракты collection, атрибуции и согласия. Перенести воспроизведения из диагностического набора в целевые регрессионные тесты.
2. Исправить приём событий, разделение целей, атрибуцию и очистку путей: CS-01, CS-02, CS-03, CS-05. Одновременно внедрить базовые ограничения CS-16.
3. Исправить жизненный цикл сайтов и миграции: CS-04, CS-06, CS-09, CS-12, CS-17. Отдельно подготовить отчёт о сиротах и невалидных ID существующей базы.
4. Исправить транспорт и интерфейс: CS-10, CS-11, CS-13, CS-14, CS-15. Обновить зависимости CS-08.
5. Проверить интеграцию согласия CS-07 в настоящих браузерах и выполнить CS-18.

Обязательный сквозной сценарий: создать сайт → подключить сниппет → внешний вход → просмотр → показ баннера → согласие → цель → повторная цель → внутренний переход → сверить общую статистику и фильтр источника → изменить collection → повторить отправку → удалить сайт → подтвердить отсутствие всех данных → создать тот же ID заново → убедиться в нулевой истории.

Исправление обработчика не исправляет уже испорченные агрегаты. После CS-02 нельзя гарантированно вычесть все ложные просмотры из каждого разреза: исходные события не сохранялись, настройки могли меняться. Подготовить оценку затронутого периода, отметить границу корректного сбора и выполнять только доказуемые преобразования с сохранением исходной резервной копии. Не обнулять историю и не объявлять её восстановленной без оснований.

Результат работ разработчика: изменения кода, регрессионные тесты, миграции и инструкции отката, обновлённые README/контракты, отчёт о проверках и отдельно — перечень исторических данных, которые невозможно надёжно восстановить.
